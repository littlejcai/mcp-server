# skill-hub 演进路线图（公开·完整版）

> 设计依据见 [ARCHITECTURE.md](ARCHITECTURE.md)（第一性原理：能力中介三公理）。
> 三条贯穿原则：**单机体验永不牺牲；契约向后兼容；安全边界每版如实公示。**

---

## 0. 阅读指南

- 演进分 **七个里程碑（M0–M6）**，构成五个递进台阶。
- 每个里程碑固定四要素：**递进逻辑**（为什么此刻做这个）、**交付物**、
  **验收门**（不满足不得进入下一阶段）、**本阶段明确不做**。
- 状态标记：✅ 已完成 ｜ 🔨 进行中/下一步 ｜ 📋 规划中。
- 功能与依赖的完整映射见第 3 节总表；度量与风险见第 4、5 节。

---

## 1. 演进全景（阶梯图）

```
 M0 个人工具 ──► M1 平台地基 ──► M2 信任隔离 ──► M3 产品可用 ──► M4 开源发布
    ✅ v0.1        🔨 v0.2         📋 v0.3         📋 v0.4        📋 v1.0
 "我自己能用"     "别人能演化"     "敢给陌生人用"    "非命令行能用"   "社区敢采纳"
                                                              │
                              ┌───────────────────────────────┘
                              ▼
                 M5 生态扩展 ──► M6 规模平台
                    📋 v1.x        📋 v2.x
                 "第三方能参与"    "组织能规模化部署"
```

**递进总逻辑**：每一层解决一个"能不能"的问题，且后一层建立在前一层的
验收门之上——

| 台阶 | 解决的问题 | 不先做它会怎样 |
| --- | --- | --- |
| M1 地基 | 能不能**演化**（改结构不破坏行为） | 后面所有功能都堆在一次性脚本上 |
| M2 隔离 | 能不能**信任**（陌生人提交的代码敢执行吗） | 上传=开门揖盗，多用户=共享单把钥匙 |
| M3 产品 | 能不能**上手**（不用读源码、不用命令行） | 没有隔离和授权的 UI 是危险品 |
| M4 发布 | 能不能**采纳**（社区敢用、敢依赖） | 契约漂移会杀死所有早期采用者 |
| M5 生态 | 能不能**参与**（第三方写驱动/技能/文档） | 无治理的生态是垃圾场 |
| M6 规模 | 能不能**长大**（组织级部署） | 单机哲学永远保留，规模化必须可选 |

## 2. 里程碑详情

### M0 · v0.1 个人工具 ✅（当前 main）

**主题：跑通最小闭环，验证核心假设。**

已交付：局域网 HTTP + Bearer 鉴权；脚本型（stdin/stdout envelope）与
Agent 型（Claude Code 无头 + allowedTools 白名单）双链路；路径围栏
（x-path-scope）、最小环境变量、超时杀进程树、全局并发 1、JSONL 审计、
错误脱敏；统一 JSON envelope 契约与多 Action 规范。

已验证：53 用例全绿、覆盖率 92%；Node 官方 SDK 第三方客户端 6/6 实测；
5 路并发串行化确认；Agent 全链路 26–47s 实测。

**已知的、留给后续里程碑的问题**（如实）：`dry_run` 调用方可绕过；
`network: false` 未强制；单 token 单用户；慢技能阻塞调用方；registry
无版本化 manifest；异步执行缺失。

---

### M1 · v0.2 平台地基 🔨（下一步）

**递进逻辑**：第一刀不是加功能，而是让结构可演化。没有包分离、契约成文
和作业模型，后续每个功能都在加深技术债。

**交付物**：

- [ ] 包重组：`skillhub/core|exec|jobs|authn|server|cli` monorepo
- [ ] `docs/CONTRACT.md`：envelope 契约 v1 成文 + 机器可读 schema + 版本与弃用政策
- [ ] `skillhub validate` / `skillhub test <skill-dir>`：契约符合性测试套件
- [ ] 作业模型：`run_skill_async → job_id`、`get_job`、内存 JobStore、
      MCP 进度通知流式输出
- [ ] 每技能并发度字段 `concurrency`（替代全局硬编码信号量）
- [ ] **`dry_run` 平台强制**（主体 scope 决定可否覆盖；read_only 技能只读执行）
- [ ] 技能 manifest 化：每技能目录 `skill.yaml`（id/version/权限/入口 +
      内容哈希），registry.yaml 变为索引；`skillhub migrate` 迁移工具
- [ ] REST API 骨架（/api/skills, /api/jobs），与 MCP 同源同权
- [ ] 官方 Node 技能示例（证明契约语言无关）

**验收门（Gate-1）**：① 53 用例全绿 + 新增用例，覆盖率不低于 92%；
② 一个 60s Agent 技能执行期间，其他客户端的短技能调用正常返回；
③ 按 CONTRACT.md 用第三方语言写的技能，不经改动能通过符合性套件；
④ `skillhub migrate` 对现有 registry.yaml 零损耗迁移。

**本阶段明确不做**：UI、上传、多用户、Docker——全部依赖本阶段产物。

---

### M2 · v0.3 信任与隔离

**递进逻辑**：M1 的 manifest 定义了"技能是谁"，本阶段回答"凭什么信它"。
隔离（A1）与多主体（A2）落地后，才存在"安全地上传"和"多租户"的可能。

**交付物**：

- [ ] docker 执行驱动：默认无网络、只读根 fs、非 root、cap-drop ALL、
      cgroup 资源上限；wsl 驱动（Windows 开发折中）
- [ ] docker-compose 一键部署（hub + 可选 redis）
- [ ] 多主体认证：users.yaml 多 token → JWT → OIDC（渐进）
- [ ] 授权策略引擎：`(主体, 技能, action, 风险) → 允许/拒绝`，默认拒绝；
      主体带风险上限
- [ ] 每主体配额（并发/频率）；响应过滤器（路径抹除、脱敏规则化）
- [ ] 三平台 CI 矩阵（win/linux/mac × py3.10–3.12）
- [ ] 发布工程：`skillhub new` 脚手架、Docker 镜像、pip/uv 安装

**验收门（Gate-2）**：① `external_write` 技能在 docker 驱动下注册后，
容器内发起网络请求物理失败；② 两个不同风险上限的主体，低者调用高风
险动作被策略拒绝且有审计记录；③ CI 三平台全绿；④ 默认 local 驱动的
单机安装仍是一条命令、零外部依赖。

---

### M3 · v0.4 产品可用

**递进逻辑**：有了隔离与授权，界面和上传才从"危险品"变成"产品"。
上传顺序是信任设计：先纯文本（SKILL.md），代码类等签名体系（M4/M5）。

**交付物**：

- [ ] Web UI：技能目录（风险/版本/作者）、调用记录、审计可视化、作业面板
- [ ] 用户管理界面（主体、scope、风险上限）
- [ ] 技能上传第一阶段：**仅 Agent 型（SKILL.md 纯文本）**，流程
      上传 → 契约校验 → 人工审核 → 启用（上传 ≠ 生效）
- [ ] JobStore SQLite 持久化（重启恢复历史）；worker 与 API 进程分离
- [ ] 可观测：Prometheus `/metrics`、`/version`、结构化日志可选 OTel

**验收门（Gate-3）**：① 新用户 10 分钟内走完"登录→浏览→上传 SKILL.md→
审核启用→手机 agent 调用成功"；② 关闭 UI 后 hub 所有 MCP/REST 功能不受
影响（UI 只是普通客户端）；③ 服务重启后作业历史可查。

---

### M4 · v1.0 开源发布

**递进逻辑**：发布的前提是"承诺"——契约冻结、版本语义、治理流程。
社区敢采纳的本质是敢依赖你的稳定性。

**交付物**：

- [ ] 契约 v1 冻结 + SemVer + RFC 式契约变更流程
- [ ] 技能签名（ed25519）与发布者信任级（community / verified）
- [ ] 技能上传放开到脚本型（docker 驱动强制 + 审批流）
- [ ] 官方示例技能画廊（≥6：脚本/Agent/多 Action/多语言/多风险级）
- [ ] 文档双语；CONTRIBUTING / SECURITY（披露流程）/ CHANGELOG；Apache-2.0
- [ ] 云端连接器指南（Tailscale / Cloudflare Tunnel / 反向代理）

**验收门（Gate-4）**：① 外部贡献者仅凭文档完成 fork→贡献技能→合并全流程；
② 破坏性契约变更演练：v1 契约下发布的技能在升级后无需修改即通过符合性
套件；③ 安全边界表（强制项/声明项）随发布物公开。

---

### M5 · v1.x 生态扩展 📋

**递进逻辑**：M4 之后产品的边界从"我们写"变成"社区写"——平台职责转为
提供扩展点并守护契约。

- [ ] 执行驱动生态：驱动开发接口文档化（firejail / macOS sandbox /
      远程 SSH 驱动等社区实现）
- [ ] 技能分发协议：去中心化的技能包索引规范（hub 不运营托管市场，
      只定义"如何发现与验证"）
- [ ] 协议适配层：MCP 之外的客户端桥（OpenAPI 出口、webhook 触发器）
- [ ] 企业特性：OIDC/SCIM 用户同步、审计日志导出至 SIEM、更细粒度配额
- [ ] Agent 技能增强：多技能编排（A 调 B 的审批链）、长任务检查点续跑

---

### M6 · v2.x 规模平台 📋（愿景）

**递进逻辑**：当单机真的成为瓶颈时的答案，且必须永远是"可选项"。

- [ ] 多节点执行集群：中心调度 + 边缘 worker，技能按标签调度到指定机器
- [ ] 数据面/控制面分离：执行结果与审计流式归档
- [ ] 合规方向：SOC2-ready 审计、数据驻留配置、租户级加密
- [ ] 可选托管控制面（产品化边界的探索，开源核心不受影响）

## 4. 度量指标（如何知道可以进下一阶段）

| 维度 | 指标 | 门槛 |
| --- | --- | --- |
| 质量 | 测试数与覆盖率 | 只增不降（当前基线 53 / 92%） |
| 安全 | 每版本安全边界表（强制项/声明项） | 声明项数量逐版减少 |
| 兼容 | 契约符合性套件通过率 | 发布版 100% |
| 体验 | M3 起：新用户上手时间 | ≤ 10 分钟 |
| 生态 | M4 起：外部贡献技能数、第三方驱动数 | 里程碑内 ≥ 各 1 |
| 采纳 | M4 起：安装量、issue 响应时长 | 公开仪表盘 |

## 5. 风险与回退

| 阶段 | 最大风险 | 回退策略 |
| --- | --- | --- |
| M1 | 包重组破坏行为 | 验收门①不过不合并；旧结构保留一个版本的兼容导入 |
| M2 | docker 驱动在 Windows 体验差 | wsl/local 驱动并存，local 永不废弃 |
| M3 | UI 范围失控 | UI 只是普通客户端的铁律；砍功能不砍 API |
| M4 | 契约过早冻结锁死错误设计 | v1 前用 RFC 收集真实使用反馈；冻结对象是"稳定子集" |
| M5/M6 | 生态碎片化 | 分发协议只定义发现与验证，不定义托管；驱动接口经 v1.0 冻结 |
| 全程 | 维护者带宽 | 每阶段验收门即暂停点；任何门未过，宁可延迟不降级 |
